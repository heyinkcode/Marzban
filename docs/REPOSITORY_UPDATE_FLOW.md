# 跨仓库更新与发布流程

本页维护工作流程，不记录某一版已勾选的验收结果。具体改动进入对应功能文档，历史证据按[功能归档](releases/README.md)。

## 文档各放哪里

| 内容 | 位置 |
| --- | --- |
| 产品介绍、安装、基本使用 | README 及其翻译；没有变化就不改 |
| 功能入口与边界摘要 | FORK_FEATURES |
| 操作、配置、兼容限制、接口合同 | 对应 docs 功能专页；配置变量见 [CONFIGURATION](CONFIGURATION.md) |
| 更新摘要 | CHANGELOG：日期、一句改动、专页链接 |
| API 导航与当前路径 | [接口索引](../MR_SHAW_API_AND_RELEASE.md)，不粘贴发布日志 |
| 可执行的服务端调用示例、机器可读合同 | `examples/`、`docs/contracts/`，从对应功能说明链接进入；不含真实密钥或特定网站的付款逻辑 |
| 测试、配对 SHA、Actions、镜像摘要、服务器验收 | 对应功能发布页；旧快照保留在 docs/releases |
| 通用发布门槛 | [发布检查清单](../RELEASE_CHECKLIST.md)，每次从未勾选状态开始 |

不要把更新编号、测试过程或镜像证据添加到产品首页；也不要在功能清单、接口索引、流程页重复同一份发布长文。旧首页归档只读保留，不继续追加。

## 每项功能必须交付的说明

功能代码和说明一起维护；不等上线后才补文档，也不把一段提交说明当作使用手册。复用已有的对应专页，只有独立功能才新增专页，避免同一功能出现多份互相冲突的“最新说明”。

1. **用途与状态**：解决什么问题，适用于主控、Node还是脚本；明确“开发中 / 本地验证 / 镜像已发布 / 服务器已验收”的实际范围，不能混用。未做的界面和受限协议也要直接写明。
2. **入口与操作**：真实的菜单/弹窗位置、必要权限、前置条件、设置顺序、保存或生效的判断。仅有API时明确没有界面入口，不写尚不存在的点击步骤；界面完成后再补真实组件截图，不用效果图代替验收。
3. **配置与接口**：参数、默认值、必填项、认证和授权、完整路径/方法、请求/响应、错误及副作用；涉及重启、等待同步、幂等、超时重查的都要说明。无接口变化也明确注明。
4. **兼容与保护边界**：支持的协议/版本、旧部署行为、对其他节点和用户数据的影响、哪些情况不支持；不把“隐藏订阅”或“收到ACK”写成未验证的硬隔离。
5. **更新、故障与恢复**：是否需要更新主控/Node/scripts，备份、迁移、回退限制、常见失败及安全处理；功能未发布时不提供看似可获取它的正式更新命令。
6. **调用与验收**：需要对接时提供脱敏请求示例或通用客户端，说明后端Token保存方式；实际测试环境、通过/失败/跳过项、待验收范围放在对应发布页，不把合成测试写成真实客户或支付验证。
7. **导航与归档**：同步文档中心、功能概览、受影响接口索引及CHANGELOG短摘要；对应发布页留证据链接。历史全文与原作者信用保留，移动文件后修复入口和锚点。

不适用的项目写明“无变化/不适用”和原因，不为凑齐目录生成空白手册。发现代码和说明不一致时，以已核对的实现修正文档；不能仅替换标题或状态标签而保留过期操作正文。

## 一次更新的顺序

1. 确定影响范围：主控、Node、scripts 分别写明「有变化」或「无运行时变化」。记录基线、备份、兼容要求和回滚方案。
2. 在独立分支修改代码与对应合同。保留原 React/Chakra 组件、证书、端口、用户、数据库、.env、数据卷及固定 Xray v26.3.27。UI 变化先展示原组件效果。
3. 测试后再推送。记录真实环境、执行数量、跳过项和失败修复过程；单测、二进制预检、真实跨服务器验收不能互相替代。
4. PR 检查通过再合并；运行时变更等待正式构建。核对镜像 index、架构 manifest/config 与 revision，不能只看 Actions 绿色或 latest 标签。
5. 按功能要求升级配对组件，再执行逐台服务器和客户端验收。发布完成、服务器验收完成是两个独立状态。
6. 在功能发布页回写证据，CHANGELOG 只留摘要。纯文档整理用 `[skip ci]`，不为文档重新打包业务镜像。

## 上架前的仓库收口

- 功能先完善并完成对应验证，再提交上架；每次PR明确列出功能、文档、测试和三个仓库的影响。需要实际UI确认的变更未确认前不进入发布。
- 提交内容按文件白名单检查；不把本地checkout、`.cache/`、虚拟环境、`node_modules/`、构建缓存、临时备份、原始日志、真实数据库、`.env`或生产凭据带入线上。必要截图只能使用脱敏的实际组件验收图，并归入对应功能，不放根目录。
- 保留上游必须存在的根目录文件、署名和许可证；不为“整洁”删除历史、用户文件或任意重排代码。已有根目录功能/API/检查入口保持兼容，详细内容归入`docs/`，不新增一堆根目录发布说明。
- 本机绝对路径不能作为公开文档的下载/调用入口；公开示例使用通用地址，仓库内使用相对链接，版本证据使用可核对的源提交/构建链接。离线本地日志只能作开发定位，不能成为读者必须访问的前置条件。
- 检查文档中心能到达功能专页、接口/示例和对应发布页，链接/锚点/代码块有效；原README及翻译没有混入更新流水账。检查仓库树和敏感信息后才提交，远端尚未核对的状态不得勾选完成。

## 升级与回滚

新服务器才 install；首次从官方切换 Fork 才 adopt；已有 Fork 使用 update。保留原部署目录与命令名，不用重装、删卷、覆盖 .env 或重建证书升级。脚本命令和备份要求见[部署仓库](https://github.com/heyinkcode/Marzban-scripts/blob/master/README.md)；误报官方镜像见[识别修复](https://github.com/heyinkcode/Marzban-scripts/blob/master/docs/UPDATE_IMAGE_RECOGNITION.md)。

升级前保存实际镜像摘要、配置及数据备份。失败按对应版本恢复配对镜像和备份；数据库迁移必须单独核对回滚风险。不能把容器 Up 当作用户业务、订阅、出口或中转均已验收。

## 接口变更最小登记

记录 HTTP 方法与完整路径或 RPyC 方法、认证权限、请求类型和默认值、脱敏规则、成功响应、错误码、数据库/缓存/重启副作用、Node 能力与旧版本行为、订阅兼容、迁移和回退、契约及隔离测试。只改 UI/文档也要明确接口与运行时是否不变。

发布记录要包含源提交、合并提交、配对版本、构建链接、镜像摘要、验证环境和结果、未验收项及恢复步骤。不要提交真实凭据、订阅 Token、原始 HWID、私钥或完整敏感日志。

整理旧说明时，先完整保存带日期和不可变源链接的历史原文，再更新现行指南；不能只在顶部加一条免责提示，却让正文继续要求不存在的新 Relay 条目或已失效的升级方式。检查相对链接、目录锚点、导航可达性、代码块及运行时/首页无差异后，才发布纯文档提交。
